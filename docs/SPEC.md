# Kasha — итоговое техническое задание, 11 сентября 2026

## 1. Назначение продукта

Kasha — локальное приложение с локальным ИИ для голосовых заметок и задач.

Основной сценарий:

**Записать голос → локально транскрибировать → при необходимости привести текст в порядок → выбрать «Заметка» или «Задача» → выбрать проект → сохранить локально.**

Ключевой продуктовый принцип: **данные пользователя принадлежат его устройству**. Аудио, транскрипции, проекты, заметки, задачи, настройки и AI-обработка не должны требовать аккаунта, облачного backend, удалённой БД или внешнего LLM API.

## 2. Архитектурный принцип

В проекте должно быть одно отделяемое ядро — `kashaCore`.

```text
                         kashaCore
        models · domain · rules · contracts · AI ports
                              │
                    общий presentation/UI
                              │
          ┌───────────┬───────┴───────┬───────────┐
        Desktop     Android          iOS          Web
          │            │              │            │
       platform      platform        platform     platform
       adapters      adapters        adapters     adapters
```

`kashaCore` содержит всё, что может одинаково работать более чем на одной платформе:

- модели данных;
- бизнес-правила;
- сценарии заметок, задач и проектов;
- правила сортировки;
- постоянный ручной порядок;
- контракты хранения, записи, воспроизведения и локального ИИ;
- проверки корректности данных и результатов AI-обработки.

Платформенный слой содержит только то, что действительно зависит от платформы:

- entry point и lifecycle;
- доступ к микрофону и разрешениям;
- воспроизведение аудио;
- конкретное файловое/БД-хранилище;
- интеграцию с конкретным локальным AI runtime;
- platform packaging;
- platform-specific API, если без него невозможно.

Архитектурное правило проекта: **если логика может одинаково работать хотя бы на двух платформах, она не должна жить в платформенном приложении.**

Core не зависит от UI. Общий Compose UI зависит от Core. Платформенные приложения подключают Core и общий UI и добавляют минимальный адаптерный слой.

## 3. Local-only и приватность

Production Kasha не должна:

- отправлять пользовательские данные во внешние AI API;
- иметь серверную пользовательскую БД;
- требовать аккаунта;
- синхронизировать заметки через облако;
- содержать telemetry/analytics SDK, которые передают пользовательские данные наружу;
- зависеть от облачного сервиса для основной функциональности.

Desktop runtime может поднимать локальный HTTP на `127.0.0.1` для Web UI. Это считается локальным транспортом внутри устройства, а не backend-сервисом.

CI должен автоматически запрещать появление известных cloud AI, analytics и sync SDK в продуктовых модулях.

## 4. Разделы приложения

Нижняя навигация содержит четыре раздела:

1. **Главная**
2. **Проекты**
3. **Задачи**
4. **Настройки**

Плеер остаётся глобальным и доступным во всех основных сценариях, где это не конфликтует с модальным действием.

## 5. Главная и голосовая запись

При открытии приложения:

- если приложение ещё инициализируется — показывается splash screen;
- после запуска пользователь попадает на Главную;
- если включён автозапуск записи и нет незавершённой записи — запись может стартовать автоматически после проверки разрешения.

Во время записи:

- крупный таймер;
- реальная осциллограмма микрофонного сигнала;
- пауза / продолжение;
- завершение записи;
- навигация по другим разделам не должна уничтожать запись.

Одновременно записывать и воспроизводить аудио нельзя.

Если пользователь пытается включить источник заметки во время записи, показать подтверждение остановки записи перед воспроизведением.

## 6. Обработка записи

После остановки:

1. исходное аудио передаётся локальному распознавателю;
2. получается полный транскрипт;
3. формируется заголовок;
4. при необходимости аудио оптимизируется и сохраняется локально;
5. запись становится доступна для редактирования и отправки.

Кнопка **«Привести в порядок»**:

- исправляет пунктуацию и структуру;
- убирает случайные повторы;
- может нейтрализовать мат по текущим правилам продукта;
- не должна терять мысли, числа, имена и отрицания;
- не должна придумывать факты;
- полный исходный смысл должен сохраняться.

Core обязан проверять AI-результат и отклонять явно разрушительные изменения.

## 7. Отправка записи: Заметка / Задача

После нажатия «Отправить» открывается экран назначения.

В верхней части экрана расположен переключатель:

**Заметка | Задача**

После выбора типа пользователь выбирает проект.

### 7.1. Заметка

После выбора проекта:

- создать новую заметку; или
- добавить текст в конец существующей заметки.

При добавлении в существующую заметку:

- старый текст не переписывается;
- новый текст добавляется строго в конец;
- аудиоисточник сохраняется отдельным источником;
- повторное сохранение одной записи не создаёт дубль.

### 7.2. Задача

Задача на текущем этапе — максимально простая сущность:

- текст;
- дата создания;
- дата изменения;
- постоянный ручной порядок;
- внутренне может хранить `projectId` источника.

В пользовательском интерфейсе задача пока отображается как простой текст в списке. Чекбоксы, дедлайны, статусы, исполнители и вложения на этом этапе не добавлять.

Одна голосовая запись не может одновременно стать и заметкой, и задачей.

## 8. Проекты

Проект содержит:

- название;
- необязательное описание/инструкцию;
- дату создания;
- дату изменения;
- признак закрепления;
- ручной порядок.

Если проектов нет, при первом запуске создаётся «Твой первый проект» на языке интерфейса.

Проект можно:

- создать;
- открыть;
- редактировать;
- закрепить;
- сортировать;
- переставлять вручную.

Для AI-подбора проекта по голосовой записи используется отдельный relevance-порядок. Пользовательская сортировка списка проектов не должна ломать AI-подбор назначения.

## 9. Сортировки

Для **проектов, заметок и задач** доступны четыре режима:

1. **По алфавиту**
2. **По дате создания**
3. **По дате изменения**
4. **Вручную**

Ручной порядок является самостоятельным постоянным состоянием.

Пример:

- пользователь выбирает «Вручную»;
- расставляет элементы;
- переключается на «По дате изменения»;
- затем возвращается на «Вручную»;
- прежняя ручная раскладка должна восстановиться полностью.

В режиме «Вручную» закрепление не должно незаметно переставлять элементы и нарушать пользовательский порядок.

## 10. Ручная перестановка

В режиме **«Вручную»**:

- элемент можно зажать long-press;
- после удержания перемещать вверх/вниз drag-жестом;
- порядок сохраняется после завершения drag;
- механизм общий для проектов, заметок и задач;
- после перезапуска порядок сохраняется.

В остальных режимах drag-reorder отключён.

## 11. Задачи

Раздел **«Задачи»** — отдельный пункт нижней навигации.

На текущем этапе:

- один простой список;
- карточка содержит только текст задачи;
- те же четыре сортировки;
- long-press reorder в ручном режиме;
- редактирование текста должно поддерживаться на уровне Core/repository, даже если минимальный UI редактирования будет добавляться постепенно.

Не усложнять Tasks до полноценного task manager на этом этапе.

## 12. Kasha UI

`Brain UI` полностью переименовать и заменить на **Kasha UI**.

В продукте должен существовать только один слой общих контролов:

- KashaButton;
- KashaIconButton;
- KashaQuietButton;
- KashaField;
- KashaEditableNote;
- KashaSwitchRow;
- KashaSlider;
- KashaPanel;
- KashaListCard;
- KashaNavigationItem;
- KashaWaveform;
- KashaProcessingRing;
- KashaCaptureMark;
- KashaSortBar;
- KashaDestinationSwitch;
- KashaReorderableList.

Продуктовые экраны не должны собирать альтернативные версии тех же контролов напрямую из Material.

Material используется как техническая база Compose, но внешний вид Kasha не должен восприниматься как Android/Material Design.

## 13. Иконки

В продуктовом интерфейсе используются **только Phosphor**.

Требования:

- никаких Material Icons;
- никаких SF Symbols;
- никаких Lucide и других параллельных наборов;
- состояние покоя визуально остаётся Phosphor;
- для интерактивных иконок используется motion из открытых animated-Phosphor реализаций;
- исходники/лицензии third-party фиксируются в репозитории;
- React/Motion не являются runtime-зависимостью Kasha: анимации портируются в Compose Multiplatform.

Основной внешний источник motion зафиксирован на конкретном commit `ln-dev7/icons-animated`; для отсутствующих glyphs допускается аккуратный motion в том же временном и пластическом языке, но геометрия остаётся Phosphor.

Анимации функциональные: короткая реакция на hover/press/focus, не бесконечный декоративный цикл.

## 14. Типографика

Основной шрифт Kasha: **Commissioner**.

Причины:

- выразительнее стандартных UI-grotesque;
- хорошо подходит под спокойную premium/Apple-like эстетику;
- хорошо читается на мобильных размерах;
- полноценная кириллица;
- поддержка русского, украинского, белорусского и казахского;
- OFL.

Использование:

- UI text: Commissioner 400 / 500 / 600;
- крупные заголовки: Commissioner 600 с очень небольшим `FLAR=10`;
- без чрезмерно декоративных начертаний.

Мобильная шкала:

- body: 15–17sp;
- small body: 13sp;
- navigation/helper labels: не меньше 11sp;
- headline: 20–28sp;
- display: максимум 46sp.

Build script обязан проверять наличие символов всех восьми языков Kasha.

## 15. Цвет и визуальный характер

Цель — спокойный, минималистичный, дорогой интерфейс ближе к дизайну Apple и дальше от типового Android UI.

### Светлая тема

На первый взгляд белая, но при внимательном рассмотрении имеет очень небольшое тёплое жёлто-бумажное смещение.

Базовый фон: приблизительно `#F7F5EE`.

### Тёмная тема

На первый взгляд чёрная/очень тёмная, но с небольшим тёплым коричневым смещением.

Базовый фон: приблизительно `#191715`.

Не использовать:

- яркий Material-синий как системный акцент;
- неон;
- стеклянные AI-эффекты;
- сине-фиолетовые glow-градиенты;
- визуальный шум.

## 16. Бренд и splash screen

Официальный логотип Kasha существует в двух версиях:

- regular;
- solid.

Использовать только официальный знак.

Не рисовать приблизительные копии логотипа.

Логотип можно использовать:

- крупно на пустой/стартовой Главной;
- на splash screen;
- в packaging/app icon там, где это уместно.

Splash screen:

- фон текущей темы/бренда;
- крупный официальный логотип по центру;
- номер версии приложения внизу;
- без прогресс-баров и лишнего текста, если загрузка не требует отдельного состояния ошибки.

## 17. Настройки

Сохранить:

- автозапуск записи;
- автоматический переход к выбору проекта после обработки;
- качество сохраняемого аудио;
- скорость сохраняемого аудио;
- язык интерфейса;
- тема.

Языки:

- Русский;
- English;
- Español;
- Français;
- Deutsch;
- Українська;
- Беларуская;
- Қазақша.

Для неподдерживаемого системного языка fallback — English.

В настройках или информационном блоке явно отражать принцип: **все данные и ИИ работают на этом устройстве**.

## 18. Аудио

Whisper/другой локальный STT получает исходный темп до ускорения и потерь сжатия.

После успешной обработки допускается хранить оптимизированную локальную версию аудио.

По умолчанию:

- mono;
- экономное качество;
- сохранённая скорость 1,5×;
- диапазон скорости 1–2×.

Временный исходник удаляется только после успешной обработки и публикации итогового локального файла. При ошибке источник сохраняется для повтора.

## 19. Независимость платформ

Ни одна конкретная платформа не должна становиться архитектурным центром продукта.

Desktop, Android, iOS и Web — клиенты одного Core-контракта.

Различаться могут:

- микрофон;
- filesystem/DB adapter;
- playback;
- permissions;
- lifecycle;
- конкретный локальный AI runtime;
- platform packaging.

Не должны различаться без веской причины:

- модели;
- правила заметок/задач;
- сортировки;
- manual order;
- validation;
- основной UI flow;
- тексты продукта;
- Kasha UI tokens/components.

## 20. Автоматические архитектурные проверки

CI должен проверять:

1. сборку `kashaCore`;
2. тесты Core;
3. общий Compose UI;
4. runtime;
5. desktop;
6. production WebAssembly;
7. browser smoke flow;
8. local-only boundary;
9. Kasha UI boundary;
10. запрет сторонних icon packs;
11. поддержку символов всех восьми языков шрифтом.

## 21. Проверка пользовательского сценария

Минимальный end-to-end сценарий:

1. запуск → splash → Главная;
2. начало записи;
3. пауза / продолжение;
4. навигация во время записи;
5. остановка;
6. локальная транскрибация;
7. редактирование текста;
8. «Привести в порядок»;
9. «Отправить»;
10. выбор «Заметка»;
11. выбор проекта;
12. новая заметка / дописывание существующей;
13. новая голосовая запись;
14. выбор «Задача»;
15. выбор проекта;
16. задача появляется в разделе «Задачи»;
17. проверка четырёх сортировок для проектов, заметок и задач;
18. ручная перестановка long-press + drag;
19. переключение на другую сортировку и возврат к Manual — ручной порядок сохранён;
20. перезапуск приложения — данные и manual order сохранены;
21. весь сценарий работает без передачи пользовательских данных во внешнее облако.

## 22. Критерий архитектурной готовности

Архитектура считается соответствующей задаче, если `kashaCore` можно отделить от конкретного приложения, подключить к новой платформе, реализовать небольшой набор platform ports и получить тот же продуктовый Core без переноса/копирования бизнес-логики.

Цель: **максимум общего кода, минимум платформенного слоя, никакой облачной обязательности.**
